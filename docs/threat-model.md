# VeloxFetch threat model (Phase 12)

What we defend, against whom, where each defence lives, and how it is checked. Every row names a test or a
command, so a claim here can be re-verified. The gate that runs all of it: `node scripts/security-gate.mjs`.

## Assets

1. **The user's files and system**: nothing a remote party controls may write outside the download folder, run code, or read local files.
2. **Secrets**: cookies and passwords handed over for a download, the database sealing key, the browser link token.
3. **The user's local network**: a web server must not be able to use VeloxFetch as a probe of local services.
4. **The installer and the update path** (what the user runs, and how new versions arrive).

## Actors

| Actor | Can do | Cannot do |
|---|---|---|
| Malicious website / link author | choose URLs, redirects, filenames, headers, bodies, playlists | run code on the machine, touch the UI |
| Malicious server | answer anything, lie about sizes / ranges / names / types, redirect | be trusted for checksums, choose a path |
| Compromised browser extension | send `download` / `ping` messages through the native host | send anything else, reach the UI IPC, skip validation |
| Malicious downloaded file | be dangerous when opened | be opened, run or previewed by VeloxFetch |
| Other program of the same user | read files the user can read | (out of scope: it can already do what the user can, see limits) |
| Network attacker | observe / alter unencrypted traffic | break TLS (rustls, certificates verified) |
| Supply-chain attacker | publish a bad crate / npm package / action | get it in unnoticed: see 12.3 |

## The IPC pipeline (12.1): every command, in this order, no shortcuts

```
webview ──► Tauri capability ──► authz.rs ──► serde schema ──► validate.rs / path-safety ──► manager ──► engine
            (per window,        (per window,   (deny_unknown    (URL, name, sub-folder,       (limits,    (re-checks the
             allow-<command>)    per command)   fields, types)    limits, sealed secrets)       state)      folder before writing)
```

| Stage | Implementation | Verified by |
|---|---|---|
| Input / schema | every command takes a typed struct with `deny_unknown_fields`; no free-form JSON, no paths from the UI | `desktop-ipc.mjs` (hostile input against the real app), unit tests |
| Authorization | 90 commands, each with an `allow-<command>` permission; one capability file per window; no `core:default`, no plugin permissions | `authz.rs` consistency tests; `tests/security/policy.test.mjs` |
| Path validation | UI can only choose a relative sub-folder; names checked strictly; `ensure_within` resolves links | `fs_security.rs`, `path-safety` tests, fuzz test |
| Business validation | URL scheme/length/credentials, checksum format, limits, categories, speed range | `validate.rs` tests, fuzz test |
| Execution | the manager owns state; the engine re-checks the folder before create / resume / rename | `fs_security.rs` (folder swapped for a link) |

The frontend is never trusted: the UI holds no secret, no path and no segment address; it sends ids and small typed values.
There is no `fetch`, no plugin, no `eval`, no `innerHTML` in the UI source (policy test).

## Localhost security (12.2)

**There is no localhost API.** The browser talks to the app over a per-user **named pipe** (Windows) or **Unix socket** (macOS / Linux),
through the browser's own Native Messaging host, which the browser starts only for the exact extension id.
One TCP socket is opened by shipped code, on Linux and macOS only: the private live-preview address (WebKitGTK's
player cannot read a custom protocol, and WKWebView's cannot stream a growing file through one;
`preview_server::loopback`, threat 32), built to 12.2 and pinned by `policy.test.mjs`. No other
TCP or UDP socket is opened (`policy.test.mjs`). If another one is ever added, 12.2 applies in full
(127.0.0.1 only, random short-lived token, strict methods and schemas, rate limits, `Origin` check, no wildcard CORS) and the policy test must be changed on purpose.

What protects the link anyway: caller allow-list (extension ids), mutual HMAC authentication with a per-launch token (never sent over the link),
message size and rate limits, a closed command set, silent-peer timeouts (`browser-bridge` tests, `desktop-browser.mjs`, `real-browser.mjs`).

## Assumptions and non-goals

* The operating system, the user account and the hardware are not compromised. A process with the user's rights is out of scope (it can read the user's files directly).
* The download folder is chosen by the app; a hostile *other* user of the same PC with write access to it is outside the model (permissions on the folder are the OS's job).
* VeloxFetch does not scan files for malware and does not open them. It marks them so the OS does.
* Denial of service by bandwidth or disk use is limited by the user's own settings (speed limits, queue), not by the app guessing intent.

## Review checklist for a new feature

1. Does it add a command? Add its `allow-` permission, a typed struct with `deny_unknown_fields`, validation, an entry in `authz.rs` and the tests.
2. Does it open a socket or a listener? Then 12.2 applies and `policy.test.mjs` must be changed on purpose.
3. Does it write a file? Names through `path-safety`, folder re-checked, no-follow open, marked as downloaded.
4. Does it fetch a URL from data it received? Apply `resolve_url` rules: http(s), no credentials, no downgrade, no public-to-local jump.
5. Does it hold a secret? It goes through `secrets`, never into a log line or a DTO.
6. Does it add a dependency? `cargo deny check` and `cargo audit` must stay green; a new licence, source or plugin needs a reason in `deny.toml`.
